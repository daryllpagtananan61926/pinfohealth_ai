# Plan-Then-Build Quick Reference

## Use the `/plan` Command

Instead of asking for code directly, ask me to plan first:

### ✅ Correct Approach
```
/plan Design a structured layout for my new database schema. Do not modify any physical files yet.
```

### ❌ Avoid This
```
Create a database schema for user management (this will make me write code immediately)
```

## What Happens When You Use `/plan`

1. **I enter planning mode** - No code is written yet
2. **I create a detailed design document** - Saved as `.plan.md` in your workspace
3. **I request your review** - You get to validate the approach before implementation
4. **You approve when ready** - Say: *"The plan is perfect. Execute the code changes now."*
5. **I execute the approved plan** - Only then do I write actual code

## Example: Complete Workflow

### Request (with /plan)
```
/plan Design a user authentication database schema including tables for users, roles, permissions, and sessions. Include migration strategy and indexes.
```

### What You'll See
- Detailed `.plan.md` file appears in the workspace
- Plan includes:
  - Schema design with all tables
  - Entity relationships
  - Indexing strategy
  - Migration plan
  - Security considerations
  - Rollback approach

### Next Step
After reviewing the plan, simply say:
```
The plan is perfect. Execute the code changes now.
```

### Result
- Schema files are created
- Migration scripts are written
- Types/interfaces are generated
- Documentation is updated

## Key Benefits

| Benefit | How It Helps |
|---------|-------------|
| **Token Efficiency** | Validate before expensive implementation |
| **Rate Limit Safety** | No wasted API calls on wrong approaches |
| **Quality Design** | Review architecture before code |
| **Audit Trail** | Plan documents explain all decisions |
| **Parallel Work** | Review while other tasks continue |

## When to Use `/plan`

- **Database schema design** - Complex data models
- **Architecture changes** - New components or modules  
- **Refactoring** - Significant restructuring
- **Integrations** - New services or APIs
- **Complex features** - Multi-step implementations
- **Framework setup** - New tools or libraries

## When NOT to Use `/plan`

- Single file edits
- Simple bug fixes
- Documentation updates
- Quick debugging sessions
- Minor changes (< 3 files)

## Approval Phrases

Any of these phrases will trigger implementation:
- ✅ "The plan is perfect. Execute the code changes now."
- ✅ "Approve the plan, let's implement it."
- ✅ "Good, execute this plan."
- ✅ "Proceed with the implementation."

---

**Pro Tip:** Use `/plan` for any large-scale work. It saves tokens and prevents mistakes!
