# Plan-Then-Build Safeguard Workflow

## Overview
This workspace enforces a "Plan-Then-Build" approach to prevent wasted tokens and rate limits on incorrect implementations. All non-trivial changes must be planned and reviewed before code is written.

## Workflow Rules

### Phase 1: Planning (Required First)
When a user requests architectural or structural changes, you MUST:

1. **Refuse immediate code execution** - Do not write code, modify files, or execute commands
2. **Generate a detailed plan** - Create a structured markdown document that includes:
   - Executive summary of the requested change
   - Architecture/design decisions with rationale
   - File structure and organization
   - Key implementation details
   - Dependencies and external integrations
   - Potential risks or considerations
   - Rollback strategy if needed

3. **Save the plan to workspace** - Write the plan to a `.plan.md` file for review
4. **Request explicit approval** - Ask the user to review and approve the plan

### Phase 2: Execution (Only After Approval)
Once the user confirms the plan is ready, you may:
- Modify files
- Create new files or directories
- Run commands or scripts
- Make structural changes

The user signals approval by saying phrases like:
- "The plan is perfect. Execute the code changes now."
- "Approve the plan, let's implement it."
- "Good, execute this plan."
- "Proceed with the implementation."

### Trigger Patterns for Planning

Use planning mode when the user:
- Requests database schema design or changes
- Asks to create new architectural components
- Proposes major refactoring or restructuring
- Asks to set up new frameworks, tools, or integrations
- Requests complex feature implementations
- Asks to design data models

**Exception:** Use planning mode for any request where you would need to modify more than 3 files or write more than 200 lines of code.

**Skip planning for:** Simple single-file edits, small bug fixes, documentation updates, or debugging sessions where the fix is obvious.

## Command Syntax

### Planning Command
```
/plan [description of what to design]
```

Example:
```
/plan Design a structured layout for my new database schema. Do not modify any physical files yet.
```

### Approval Command
After user reviews and approves:
```
The plan is perfect. Execute the code changes now.
```

## Implementation Checklist

When executing after approval, follow this checklist:
- [ ] Review the approved `.plan.md` file
- [ ] Create files in correct order (dependencies first)
- [ ] Follow the architecture from the plan
- [ ] Add comments explaining complex logic
- [ ] Test changes locally if applicable
- [ ] Verify no side effects or breaking changes
- [ ] Update documentation if needed

## Benefits

1. **Token Efficiency** - Validate direction before expensive implementation
2. **Rate Limit Protection** - Prevent wasted API calls on wrong approaches
3. **Quality Assurance** - Review design before code execution
4. **Audit Trail** - Plan documents serve as documentation of decisions
5. **Parallel Review** - User can review while you work on other tasks

## Example Workflow

```
User: "Create a new database schema for user management"

AI: [PLANNING MODE - Creates detailed .plan.md with schema design, ERD, relationships, indexes, migration strategy]
   
AI: "I've created a plan at `.plan.md`. Please review the schema design, relationships, and indexing strategy. When ready, say 'The plan is perfect. Execute the code changes now.'"

[User reviews plan...]

User: "The plan is perfect. Execute the code changes now."

AI: [EXECUTION MODE - Creates schema files, migration scripts, types, etc. as per the plan]
```
